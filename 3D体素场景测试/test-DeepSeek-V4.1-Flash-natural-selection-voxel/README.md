# 自然选择号 · 体素全景

> 在宇宙中飞行的「自然选择号」，整舰由程序化体素雕塑生成，沉浸式全景漫游。
> 交付物是**一个可以双击打开的 HTML 文件**，不依赖本地服务器、不需要联网。

---

## 一、怎么用

| 我想做什么 | 怎么做 |
|---|---|
| 看场景 | 双击 `自然选择号-体素全景.html`，或双击 `打开场景.bat` |
| 转视角 | 鼠标左键拖拽 |
| 推拉镜头 | 滚轮 / 双指捏合 |
| 换机位 | 点底部按钮，或按数字键 `1`–`5` |
| 暂停自动巡航 | `空格` 或点「自动巡航」 |
| 视角复位 | `R` 或点「复位视角」 |
| 隐藏界面 | `H` |
| 重新构建 | 双击 `重新构建.bat` |

五个机位：**巡航 → 舰首 → 重力环 → 引擎 → 全景**，自动循环播放；手动拖动后巡航照常继续，视角偏移只是叠加在镜头之上。

## 二、里面有什么

### 舰体（全体素雕塑，无外部模型）
| 结构 | 说明 |
|---|---|
| 舰首针锥 | 八角截面逐段收束，舰首传感器阵列 + 顶端红色信标 |
| 前舰体 | 八角形放样，顶部装甲板 / 侧面收边 / 纵向横向装甲缝 |
| 六边形指挥盘 | 参考图中带橙边的六角甲板 |
| 重力环 | 主环 R=86、管径 11，48 段交替配色，内侧一圈暖色舷窗，环外齿状散热块，外加一道细钢环；六根辐射支撑臂接到舰体 |
| 前部小环 | R=46 的传感器 / 散热环，四根辐条 |
| 背脊与舰桥 | 主背脊甲板、舰桥塔、三根桅杆天线（顶端航空障碍灯） |
| 尾部动力舱 | 四个大钟形主喷口（内部挖空 + 喉部发光）、尾部橙环、四组侧向辅助喷口 |
| 侧挂外舱 | 两只大型外挂舱 + 连接桁架 + 尾部小喷口 |
| 散热鳍 / 背鳍 | 尾部两侧薄板散热鳍，舰体上下板状突出 |
| 腹部 | 腹板、两座大型坞舱门（内透青光）、四根起落支撑柱 |
| 表面细节层 | 舷窗灯带、装甲棱线、机械细节生长（greeble）、橙色警示条 |

### 环境
- **星云背景**：AI 生成的等距柱状全景图，作为天空盒 + 环境光照（PMREM）
- **星空**：44,000 颗星，带色温差异、尺寸差异与闪烁相位
- **近景微尘**：1,500 粒，用于增强速度感
- **远景行星**：背光气态巨行星 + 环系（程序化着色器：条带、湍流、边缘大气）
- **太阳**：方向光对齐的耀斑精灵，带十字星芒
- **体素碎屑带**：4 种碎屑几何 × 110 实例，缓慢自转
- **引擎等离子体**：四主四副共八道，双锥体（外壳 + 白热内核），加性混合，带湍流噪声、冲击波条纹、喷口辉光与真实点光源

### 渲染管线
1. 场景先渲染到**半浮点 HDR 缓冲**（4× MSAA）
2. 亮部提取 → 三级高斯模糊链（1/2、1/4、1/8 分辨率）
3. 合成：泛光叠加 → 曝光 → **ACES 色调映射** → 暗角 → 胶片颗粒 → 边缘色散 → sRGB 编码

自发光体素的顶点色用 `Float32` 存储并放大 2.8 倍，直接进入 HDR 区间，所以舷窗和等离子体的辉光是真的「烧」起来的。

### 画质自适应
运行时监测帧率：低于 38 FPS 持续一段时间就下调渲染倍率，高于 57 FPS 再逐步调回。下限 0.62 倍，保证在集显笔记本上也能跑。

## 三、技术实现要点

### 体素网格引擎（`src/voxel.js`）
- `Uint8Array` 存材质编号，0 为空气
- **邻面剔除**：只有暴露在空气中的面才生成三角形，内部体素完全不产生几何
- **顶点 AO 烘焙**：每个顶点采样 3 个邻居，得到 4 档遮蔽系数，乘进顶点色，形成体素艺术标志性的缝隙阴影
- **四边形翻转**：按 AO 对角关系翻转三角剖分方向，消除斜向暗斑
- 不发光 / 自发光体素分成两份几何体，前者用 `Uint8` 顶点色省显存，后者用 `Float32` 进 HDR

### 雕塑层（`src/ship.js`）
全部为确定性程序生成（无随机种子依赖），分七个阶段：
舰体放样 → 尾部动力舱 → 侧挂舱/散热鳍 → 腹部结构 → 重力环 → 背脊/舰桥 → 表面细节层。

### 三个工程坑（已修，写下来备忘）
1. **细节级联生长**：在 `forEachExposed` 遍历过程中直接往暴露面外侧加方块，新方块自己也会被判定为「朝上暴露」，于是沿 Y 轴一路长成尖塔。必须**先收集坐标再统一落地**。
2. **自建泛光链的缓冲复用**：每级模糊必须让结果固定落在该级的主缓冲里，中途换引用会让第 1 级缓冲混入第 2 级能量，泛光看起来发灰。
3. **浮点体素坐标（最阴的一个）**：雕塑代码里到处是 `for (let dx = -rr; dx <= rr; dx++)` 这种以浮点数为起点的循环。因为 `sy = 248`、`sz = 448` 都是偶数，`x + 0.5` 与 `y + 0.5` 相乘后小数部分恰好凑成整数，`(x*sy + y)*sz + z` 于是算出一个**看起来完全合法**的下标——但对应的格子已经偏移了 `Y + 124` / `Z + 224`。表现是舰体上凭空长出 2794 根贯穿整个网格的细柱，共 29,265 个幽灵体素（占全部实体的 1.7%）。现在 `VoxelGrid` 的所有读写入口统一做坐标量化，调用方怎么写都不会再跑偏；`tools/selfcheck.mjs` 会把它挡在构建前。

   顺带修掉的：`fillBox` 在覆写已有体素（尤其是挖空喷口时 `m === 0`）只写不记账，导致 `solid` 计数器虚高 88,770。

## 五、正式包 vs 排查包

`build.mjs` 支持两种产出，**报错时先切排查包**：

```
node build.mjs            正式包，压缩 → 自然选择号-体素全景.html
node build.mjs --debug    排查包，不压缩 → _debug.html
```

正式包经 esbuild 压缩后变量会被改名，例如 `lastShotChange` 变成 `$t`。运行期一旦抛错，
控制台只剩单字母堆栈，根本没法定位——本项目就踩过这个坑：页面卡在 94% 报
`Cannot access '$t' before initialization`，换成排查包后才看清是
`bindHud() → switchShot() → lastShotChange` 的暂时性死区（TDZ）问题。

**排查流程**：正式包报错 → `node build.mjs --debug` 复现拿到可读堆栈 → 改源码 →
重跑正式包确认。排查包体积大（约 1.7 MB）且变量可读，不要拿去发布。

⚠ **两个包放在同一个目录时，启动脚本必须排除 `_` 开头的文件。**
`_` 是 U+005F，`自` 是 U+81EA，按名称排序 `_debug.html` 排在正式包**前面**。
`for %%f in ("*.html")` 会先枚举到它，结果双击"打开场景"启动的是排查包。
`打开场景.bat` 里已经用 `!N:~0,1!=="_"` 把它排掉。
